# Architecture Decisions — JobPulse

## 1. Why this Ingestion Strategy?
I chose a public RSS feed source (WeWorkRemotely) rather than browser automation against commercial job boards (like LinkedIn or Indeed) because the assignment explicitly permits a public job-board RSS/API source, and my goal was to demonstrate ingestion resilience without attempting to circumvent authentication, CAPTCHA, or anti-bot protections. 

This strategy prioritizes:
- **Reduced Evasion and Compliance Risk**: Using a permitted public RSS source avoids the need to bypass authentication, CAPTCHA, or anti-bot controls on protected platforms.
- **Architectural Isolation**: Uses an adapter interface that abstracts raw fetching from core orchestration. This proves we can ingest from any endpoint simply by mapping payload schema keys without changing the core engine.

---

## 2. Technical Trade-Off: In-Process Cron vs. Distributed Worker Queues
For the task scheduler, I used an in-process scheduling library (`node-cron`) rather than spinning up a distributed message broker (e.g. BullMQ, Redis, or RabbitMQ).

**Trade-Offs:**
- **Why this was chosen**: Keeps the deployment footprint lightweight, self-contained, and easily deployable to Render's free tier without external cache dependencies.
- **Implications**: An in-process scheduler is tied to the lifecycle of the web server. It does not scale horizontally (multiple web servers would spawn multiple independent crons, causing overlapping runs).
- **Future Scale Path**: If given a week, I would migrate the scheduling layer to a persistent distributed queue system (like BullMQ + Redis) to handle worker task locking, state persistence across crashes, and multi-node execution scaling.

**Human Verification:**

- All code generated by AI was modified where it did not strictly match the project's requirements, and was verified by passing the automated test suite.

---

## 4. Where I Stop & Fallback Strategy
- **Where I Stop**: JobPulse does not attempt to bypass CAPTCHA, authentication, fingerprinting defenses, robots/access controls, or other anti-bot mechanisms. If a source blocks requests, the system backs off, opens its circuit, records the failure, and falls back to another permitted source/adapter rather than escalating the scraping technique.
- **Fallback Plan**: When the primary source's circuit trips to `OPEN`, the system can fall back to alternative registered adapters (e.g. other public boards) or fall back to serving cached listings from the local MySQL database with a warning banner indicating that live synchronization is temporarily degraded.
